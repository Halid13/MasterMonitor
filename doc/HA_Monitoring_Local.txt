La gestion de la haute disponibilité de MasterMonitor, dans mon contexte 100% local, doit suivre un plan clair et réaliste : deux contrôleurs de domaine Active Directory avec DNS intégré, un PostgreSQL primaire avec un réplica local, deux instances de MasterMonitor derrière un load balancer local, des logs et flux temps réel centralisés en base, et une collecte de monitoring autonome qui ne dépend pas de l'ouverture du dashboard. Cette architecture ne cherche pas la complexité maximale ; elle cherche la continuité de service avec une exploitation simple et fiable sur le LAN, le tout déployé sur six VM hébergées sur une seule machine locale.

L'architecture ciblée s'articule autour d'un principe : chaque service critique doit continuer à fonctionner si un nœud tombe. Côté identité, DC1 et DC2 assurent ensemble l'authentification LDAP, la résolution DNS et la disponibilité des services de domaine. Côté données, PostgreSQL primaire traite les écritures et le réplica reçoit en continu la réplication pour prendre le relais en cas de panne. Côté applicatif, MasterMonitor est déployé sur deux instances distinctes ; les utilisateurs passent toujours par une adresse unique locale du load balancer, qui envoie le trafic vers l'instance saine. Côté observabilité, les logs ne restent plus en mémoire process : ils sont écrits en base, lus en base, et diffusés en temps réel depuis cette source partagée. Enfin, la collecte de monitoring tourne comme un service systemd autonome, ce qui garantit la mise à jour des métriques même si personne n'est connecté à l'interface.

Le schéma logique peut se lire simplement. Les utilisateurs internes accèdent à une URL locale unique. Cette URL pointe vers Nginx, hébergé sur la même VM que MasterMonitor instance 2, qui distribue le trafic vers MasterMonitor instance 1 et MasterMonitor instance 2. Les deux instances interrogent AD via DC1 et DC2 pour l'authentification et les groupes. Les deux instances lisent et écrivent dans PostgreSQL primaire, pendant que PostgreSQL réplica est maintenu synchronisé sur sa propre VM. Le service de collecte, colocalisé sur la VM du réplica, envoie ses snapshots de monitoring vers la base de données, et les écrans de supervision récupèrent les données depuis la base commune. Ainsi, la perte d'une instance applicative ne coupe pas l'accès, la perte d'un DC ne coupe pas l'authentification, et la perte d'un nœud de base n'entraîne pas de perte immédiate de service si la bascule est préparée.

Les rôles par VM sont cohérents avec ce plan. Une première VM Windows Server héberge DC1 avec DNS, une deuxième VM Windows Server héberge DC2 avec DNS, une troisième VM Debian héberge PostgreSQL primaire, une quatrième VM Debian héberge PostgreSQL réplica ainsi que le service de collecte monitoring, une cinquième VM Debian héberge MasterMonitor instance 1, et une sixième VM Debian héberge MasterMonitor instance 2 ainsi que Nginx en load balancer local. Ce découpage sur six VM permet d'isoler les pannes et d'éviter qu'une saturation sur un rôle n'impacte les autres, tout en mutualisant uniquement les rôles dont la cohabitation ne présente aucun risque opérationnel.

La pertinence de chaque bloc en HA est directe. AD/DNS est critique car sans lui l'accès administrateur est bloqué. PostgreSQL est critique car toutes les données métier et de supervision y convergent. Les deux instances MasterMonitor sont nécessaires pour supprimer le point de défaillance applicatif. Les logs en base et le stream basé sur la base sont indispensables en multi-instance, sinon chaque nœud expose une vision partielle. La collecte autonome est essentielle pour conserver des données à jour en continu, indépendamment de l'activité utilisateur.

Le plan de déploiement sans coupure se fait par superposition, jamais par remplacement brutal. On commence par préparer et sauvegarder l'existant, puis on valide la réplication AD/DNS entre DC1 et DC2. Ensuite on ajoute le réplica PostgreSQL sur sa VM dédiée, on vérifie la réplication et on teste la restauration. Puis on déploie MasterMonitor instance 2 et on met Nginx en frontal, d'abord avec une instance principale et une secondaire, puis en actif sur les deux une fois les tests terminés. Après cela, on finalise la cohérence applicative : tous les logs sont persistés en base, le flux temps réel s'appuie sur la base, et aucune fonctionnalité critique ne dépend d'un stockage mémoire local. Enfin, on active le service de collecte monitoring sur la VM du réplica et on valide que les données continuent de se mettre à jour dashboard fermé.

La validation finale doit simuler des pannes réelles, une par une : arrêt de DC1, arrêt de DC2, arrêt d'une instance applicative, arrêt du primaire PostgreSQL selon la procédure de bascule prévue. À chaque test, on contrôle quatre points : accès utilisateur, disponibilité des données, continuité des logs, et reprise normale après retour du nœud. Cette discipline transforme le plan HA en capacité opérationnelle réelle.

Avec cette version cible, le projet reste strictement local, sans dépendance cloud, tout en gagnant une haute disponibilité pertinente pour l'exploitation quotidienne : moins de risque d'indisponibilité, maintenance plus sereine, et meilleure confiance dans la supervision.

Ainsi voici le plan :

* **Active Directory / DNS** : 2 VM Windows Server (DC1 + DC2), DNS intégré, réplication AD validée.
* **PostgreSQL** : 1 VM dédiée pour le primaire, 1 VM dédiée pour le réplica, avec sauvegardes automatiques et procédure de bascule testée.
* **MasterMonitor** : 2 instances sur 2 VM Debian distinctes, Nginx en load balancer colocalisé sur la VM de l'instance 2.
* **Logs / stream** : tous les logs persistés en base, flux temps réel via la base commune, aucune dépendance à l'instance.
* **Collecte monitoring** : service systemd autonome sur la VM du réplica PostgreSQL, indépendant du dashboard.
