Lorsque nous avons entrepris la mise en place de la haute disponibilité pour l'Active Directory et le DNS dans le cadre du projet MasterMonitor, l'objectif était clair : disposer de deux contrôleurs de domaine Windows Server opérationnels sur le même réseau local, avec DNS intégré à Active Directory et réplication fonctionnelle entre les deux machines. DC1 existait déjà avec AD DS, DNS et le domaine monitor.local entièrement configurés. DC2 était une nouvelle VM sur laquelle les rôles AD DS et DNS venaient d'être installés, mais aucune configuration n'avait encore été réalisée. Ce qui semblait être une procédure directe s'est avéré nécessiter plusieurs diagnostics et corrections successives avant d'aboutir au résultat attendu.

La première difficulté est apparue dès la tentative de jointure de DC2 au domaine monitor.local. La commande Add-Computer a échoué avec un message indiquant que le domaine spécifié n'existait pas ou ne pouvait pas être contacté. Ce type d'erreur peut sembler surprenant quand le domaine est pourtant bien actif sur DC1, mais la cause était en réalité simple : DC2 était encore configurée en DHCP et son serveur DNS pointait vers la passerelle réseau (192.168.23.254) et non vers DC1 (192.168.23.141). Or, pour qu'une machine puisse rejoindre un domaine Active Directory, elle doit impérativement être capable de résoudre les enregistrements DNS SRV du domaine, qui sont hébergés par le contrôleur de domaine existant. Sans ce prérequis, la machine est aveugle vis-à-vis du domaine, peu importe que ce dernier soit parfaitement fonctionnel. L'ingénieur a diagnostiqué le problème en exécutant ipconfig /all, nslookup monitor.local et un ping vers l'IP de DC1. Une fois la cause confirmée, le serveur DNS de DC2 a été reconfiguré pour pointer explicitement vers l'IP de DC1 via la commande Set-DnsClientServerAddress, le cache DNS a été vidé et les entrées DNS enregistrées. La résolution du domaine est alors devenue fonctionnelle.

Le second problème était directement lié au premier : DC2 fonctionnait en DHCP, ce qui est totalement incompatible avec le rôle de contrôleur de domaine. Un DC doit avoir une adresse IP fixe, car ses enregistrements DNS et ses références dans Active Directory sont liés à cette adresse. Si l'IP change suite à un renouvellement de bail DHCP, les autres machines du domaine ne peuvent plus le localiser. La correction n'a pas été immédiate : la première tentative de configuration statique avec New-NetIPAddress a échoué avec le message "Instance already exists" car une IP DHCP était déjà assignée sur l'interface. La seconde tentative avec Set-NetIPAddress -DefaultGateway a également échoué car ce paramètre n'existe pas dans cette commande sous Windows Server 2022. L'ingénieur a alors appliqué la séquence correcte en plusieurs étapes distinctes : désactivation du DHCP sur l'interface avec Set-NetIPInterface, suppression de l'IP existante avec Remove-NetIPAddress, suppression de la route par défaut avec Remove-NetRoute, puis création complète de la configuration statique avec New-NetIPAddress en spécifiant l'adresse IP, le masque et la passerelle. Cette approche par suppression puis recréation est la seule fiable pour éviter les conflits liés à une configuration réseau préexistante.

Le troisième et plus sérieux problème est survenu lors de la première tentative de promotion de DC2 en contrôleur de domaine supplémentaire. La commande Install-ADDSDomainController a échoué avec un message d'erreur générique peu explicite. L'analyse du journal des événements Windows, dans le canal Directory Service, a révélé l'événement 2542 avec un message précis : le serveur d'annuaire avait détecté que la base de données avait été remplacée par une opération non supportée, et demandait la suppression de la clé de registre DSA Database Epoch dans System\CurrentControlSet\Services\NTDS\Parameters. Cette erreur est un mécanisme de protection d'Active Directory : elle se déclenche lorsque Windows détecte une incohérence entre l'identifiant de base de données stocké dans le registre et l'état réel du système. Elle est caractéristique d'une VM créée depuis un clone ou un snapshot d'une machine qui avait déjà eu un rôle AD, même de manière partielle ou avortée. Dans ce cas, la VM DC2 contenait probablement des résidus d'une tentative précédente. L'ingénieur a supprimé la clé fautive avec la commande Remove-ItemProperty ciblant la valeur DSA Database Epoch dans le registre. Cette action a levé le blocage.

Le quatrième problème n'était pas technique à proprement parler, mais méthodologique. Après plusieurs tentatives échouées et corrections partielles successives, l'état général de la VM DC2 était devenu incertain : configurations réseau partiellement appliquées, tentatives de promotion avortées à différentes étapes, et potentiellement d'autres résidus dans le registre ou les journaux système. Continuer à empiler des corrections dans cet état aurait risqué de créer de nouveaux problèmes difficiles à diagnostiquer. L'ingénieur a donc pris la décision de reprendre l'intégralité de la procédure depuis le début, de manière strictement séquentielle, en validant explicitement chaque étape avant de passer à la suivante. Cette discipline a consisté à vérifier l'IP statique et le DNS de DC2, confirmer la résolution DNS vers DC1, valider la connectivité réseau, confirmer la jointure au domaine, puis seulement relancer la promotion dans un état propre et entièrement connu. C'est cette rigueur qui a permis de finaliser la promotion sans nouvelle erreur.

Au terme de cette procédure, les vérifications finales ont confirmé que les deux contrôleurs de domaine, WIN-MasterMonitor pour DC1 et WIN-TRGA000VOUL pour DC2, sont visibles et opérationnels dans le domaine monitor.local. Les deux machines portent le rôle Global Catalog. La réplication Active Directory est fonctionnelle sur les cinq partitions du domaine (monitor.local, Configuration, Schema, DomainDnsZones et ForestDnsZones) avec zéro erreur constatée. La zone DNS monitor.local est intégrée à Active Directory et répliquée sur les deux contrôleurs de domaine.

Cette expérience met en évidence trois enseignements importants pour tout ingénieur qui met en place un second contrôleur de domaine. Premièrement, la configuration réseau statique n'est pas optionnelle : elle doit être la toute première action réalisée sur la machine, avant toute tentative de jointure ou de promotion. Deuxièmement, le DNS de la future DC2 doit impérativement pointer vers DC1 dès le départ, sans quoi le domaine reste invisible. Troisièmement, la propreté de l'état de la VM est un prérequis souvent négligé : tout résidu d'une ancienne tentative de configuration AD, qu'il soit dans le registre, dans les fichiers système ou dans les journaux, peut bloquer la promotion de manière cryptique. Une approche séquentielle avec validation intermédiaire reste toujours la voie la plus fiable, surtout lorsque des erreurs ont déjà été rencontrées en cours de route.
